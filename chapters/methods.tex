\section{Simulation methods}\label{sec:SimMethods}

In this section, the numerical methods utilised in this work are introduced.
Firstly, we focus on \acrshort{dns} which we primarily use throughout this work.
Thereafter, \acrshort{rans} are presented, as additional simulations are performed with this method.

\subsection{DNS in Neko}\label{subsec:DNSmethod}

For the simulation of turbulent flows a range of methodologies can be employed.
The decision regarding the utilisation of a specific approach depends on the characteristics of the flow and the requirements for the solution.
One straight-forward approach is the \acrshort{dns}.
\acrshort{dns} necessitates the solution of the \acrshort{nse} in order to compute $U(x,t)$.
Thus, \acrshort{dns} is the computationally most expensive approach, given that it resolves all length and time scales \citep{pope_turbulent_2015}. 
Conversely, this approach yields the most accurate results.
In the context of small turbulent scales, the utilisation of \acrshort{dns} is inevitable.
Due to the high computational demands, \acrshort{dns} is typically employed in the study of low to moderate Reynolds numbers. 
Its application is primarily restricted to research contexts \citep{slotnick_cfd_2014}.
The simulation method of \acrshort{dns} is the principal approach employed in this project.

%Developing this project involved the utilisation of a range of tools. 
%In this project, the majority of fluid simulations were performed with \acrshort{dns}. 
To execute these simulations the spectral element code \name{Neko} was used. 
\name{Neko} is an open-source code developed for \acrshort{dns} and \acrshort{les} simulations of incompressible turbulent flows.
It is the direct decendant of \name{Nek5000} which is a well-established \acrshort{cfd} implementation.
\name{Neko} is written in modern, object-oriented Fortran code \citep{jansson_neko_2024}.
It solves the \acrshort{nse} based on the high-order \acrfull{sem} which was first introduced by \citet{patera_spectral_1984}.
In \acrshort{sem} the \acrfull{fem} and spectral methods are combined \citep{patera_spectral_1984}.
Therefore, the domain is divided into small elements adding up to a mesh structure that represents the domain similar as in \acrshort{fem}.
This enables the representation of complex geometries through various element shapes and arrangements.
Additionally, the resolution of the solution can be adjusted by varying the size of the elements.
In \acrshort{fem}, the quantities inside the cells are usually calculated with low-order approximations.
Therefore, a refinement of the mesh would cause an algebraic error reduction \citep{deville_high-order_2002}. 
In order to achieve well-resolved results, it is necessary to employ meshes with extremely high element numbers. This, in turn, increases the computational costs significantly.
Hence, the spectral method was introduced by \citep{patera_spectral_1984}.
The idea of the spectral method is to use a single high-order polynomial to represent the behaviour of the complete domain.
With this approach, the error decreases exponentially with increasing polynomial order \citep{deville_high-order_2002}.
However, the spectral method is only applicable to quite simple geometries since a single polynomial cannot match complex geometries.
Therefore, the approaches are combined in the following way:
The domain is discretised in elements according to \acrshort{fem} and the solution within one element is approximated with a high-order polynomial as in the spectral method.
The high-order polynomial can be expressed as a tensor-product of 1D Lagrange interpolating polynomials \citep{deville_high-order_2002}.
Inside a single element, the polynomial is defined through a set of points.
These \benennung{\acrfull{gll}} points have a specific non-uniform distribution across the element which is visualised in \autoref{fig:gllPoints}.
Their spacing is more compact near the element boundary, thereby mitigating oscillation issues associated with high-order polynomials \citep{deville_high-order_2002}.
In \autoref{fig:gllPoints}, it is also visualised how the positions of the \acrshort{gll} points are adopted if the shape of the element is modified.
This could happen through complex domain shapes, where the element shape needs to be adapted to the shape of the domain boundaries as in the curved-wall configurations studied in this project.
Since a \acrshort{gll} point is positioned at the boundary of the element also, the number of \acrshort{gll} points is $N+1$ for representing a polynomial of order $N$.
The \acrshort{gll} points at the element boundaries ensure the continuity of the solution across element boundaries \citep{deville_high-order_2002}.
Usually, different polynomial orders are used to represent the velocity and the pressure fields to avoid spurious pressure oscillations \citep{maday_spectral_1989}.

\subsection{RANS simulations in OpenFOAM}\label{sec:RANSmethod}
%In addition to the DNS, a number of \acrshort{rans} simulations were conducted as well. 

In the course of this work, we also employed \acrshort{rans} simulations.
They are based on the already introduced Reynolds decomposition of the \acrshort{nse} (see \autoref{subsec:TBLTheory}).
The resulting equations for \acrshort{tbl} are written in \autoref{eq:rans} which enables the computation of the mean pressure and velocity fields.
The velocity fluctuations are represented in the Reynolds stress tensor. 
In order to circumvent the full computation of this tensor, a number of methodologies have been formulated for its approximative modelling \citep{wilcox_turbulence_2006}. 
Since the models differ with respect to characteristics and accuracies, the selection of the most appropriate model is of paramount importance, as it will have a substantial impact on the simulation \citep{yang_assessment_2016}.
Within the simulation, we employ the so-called $k\text{-}\omega$ SST model.
This model combines the $k\text{-}\omega$ and $k\text{-}\varepsilon$ models, incorporating an additional term for the shear-stress transport (SST) \citep{menter_two-equation_1994}:
In the sublayer of the boundary layer, the $k\text{-}\omega$ model is used due to its proven accuracy in this region. 
The $k\text{-}\omega$ model is then blended with the $k\text{-}\varepsilon$ model, which has been shown to provide more accurate results for $k$ and $\varepsilon$.
These quantities determine the eddy viscosity which is the primary information required by the mean flow solver. 
Therefore, an accurate prediction of mean flow depends on accurate values for $k$ and $\varepsilon$ \citep{menter_two-equation_1994}.
It is evident that these simulations exhibits superior computational performance in comparison to \acrshort{dns}.
In case the detailed behaviour of the turbulent scales is irrelevant, and the focus is on the effect of the turbulence on the flow, \acrshort{rans} simulations provide a reasonable compromise \citep{alfonsi_reynolds-averaged_2009}.
Consequently, this simulation method finds application in multiple industrial environments.

In order to execute these simulations, the open-source software \name{OpenFOAM} is utilised. 
This software is able to perform \acrshort{rans} simulations of fluid flows with a variety of turbulence models. 
\name{OpenFOAM} implements the \benennung{\acrfull{fvm}} to approximate the \acrshort{nse} \citep{weller_tensorial_1998}.
The numerical approximation of the \acrshort{nse} is achieved by the subdivision of the domain into finite control volumes. 
This approach stands in contrast to the \acrshort{dns}, wherein the equations are solved analytically.
For each of these cells, the equations are then integrated over the volume, thereby converting them into a sum of fluxes through the cell edges.
This property makes the method inherently conservative, since all field quantities, e.g.~pressure and velocity components, that leave a cell across an edge enter the neighbouring cell \citep{moukalled_finite_2016}. 
Therefore, mass and momentum are exactly conserved in the discretisation \citep{weller_tensorial_1998}.
Most codes are based on a so-called collocated variable arrangement, meaning that all quantities are stored at the same point in the control volume, e.g., the cell centre.
However, it is necessary to derive the field quantities at the cell edges to determine the fluxes across the cell edges \citep{schlatter_lecture_2025}.
This is usually done by interpolation of the field quantities which is visualised in \autoref{fig:FVMMethod}
A range of schemes exist for the purpose of performing this interpolation. 
Specific interpolation schemes can be utilised for individual quantities depending on their properties.
In \name{OpenFOAM} the interpolation schemes for the different variables are defined in the \texttt{fvSchemes} file.


Using the previously described approach, most variables can be successfully quantified.
However, for incompressible flows it is not possible to derive the pressure directly with this method.
The pressure manifests exclusively in a derivative, thus there is no explicit term to calculate the pressure.
Nevertheless, the prediction of the pressure must be conducted in a manner that satisfies the following condition:

The pressure field appearing in the momentum equation must be computed in a manner that ensures the resulting velocity field satisfies the continuity equation.
In order to achieve this objective, a number of methodologies can be employed to derive a pressure field that satisfies this condition with a \benennung{predictor-corrector iteration} \citep{schlatter_lecture_2025, weller_tensorial_1998}.
One commonly used approach is the \benennung{\acrfull{simple}} approach, which is also implemented in \name{OpenFOAM}.
It consists of four basic steps \citep{schlatter_lecture_2025}:
\begin{enumerate}
    \item Prediction: Estimate the pressure field and solve the momentum equations.
    \item Poisson equation: Solve the additional pressure equation for the pressure correction variable $p'$.
    \item Correction: Correct the pressure and the velocity fields with the pressure correction variable to improve the mass conservation.
    \item Repetition: update the initial values for pressure and velocities and repeat until a converged solution is obtained.
\end{enumerate}

\subsection{Neko simulation setup}

In order to derive the \acrshort{zpg} \acrshort{tbl} in a curved-wall configuration, we first need to create a general setup for the curved-wall \acrshort{tbl}. 
The initial configuration of the flat \acrshort{tbl} described in detail in \autoref{sec:flatTBL} is utilised as the basis.
A curved segment is added behind the flat \acrshort{tbl} configuration.
It is imperative to consider the flat part, as this is necessary for the optimal development of the \acrshort{tbl}. The objective is to achieve
a value of $Re_{\theta} \approx 1000$ when the wall curvature starts. 
The curved part has a constant radius and develops in negative wall-normal direction. 
Therefore, the \acrshort{tbl} experiences a convex curvature. 
At the end of the wall curvature, an additional straight segment is appended, which is called \benennung{straight outlet}.
A seamless transition is observed between the curved segment and the outlet, as the former aligns with the tangential direction of the curved segment. 

The complete setup is shown in \autoref{fig:paraviewDomain}.
The pressure \acrshort{bc} at the outflow forces the pressure to be zero.
Consequently, the pressure trend in front of the outflow is affected by the specified \acrlong{bc}.
In order to circumvent that the \acrshort{bc} impacts the pressure progression in the curved segment, the straight outlet is added.
The mesh is generated in a manner analogous to that employed for the flat \acrshort{tbl} with the addition of the curved part and the straight outlet.
The curved segment is created with a circular arc with the corresponding values for the radius and angle.
In the straight outlet the mesh is coarsened since this part of the domain is not relevant for the study of the \acrshort{tbl} over the curved wall. \\

\subsubsection{Boundary and initial conditions}
The imposed \acrshort{bc} and \acrfull{ic} are similar to those of the flat \acrshort{tbl} simulations.
The \acrshort{ic} is a \benennung{Blasius profile}, as in the flat \acrshort{tbl} simulations (see \autoref{sec:flatTBL}).

The Blasius profile is an analytic solution for the velocity profile of a laminar boundary layer over a flat plate with \acrshort{zpg} conditions \citep{blasius_grenzschichtern_1908}.
It is based on the self-similar character of the boundary layer meaning the velocity profile over the flat plate looks similar at any streamwise position once it is rescaled with the local boundary layer thickness \citep{schlichting_boundary-layer_2017}.
The outflow condition and the lower wall \acrshort{bc} are also transferred.
A \benennung{Dirichlet condition} is applied as \acrshort{bc} for the top wall.
Since the flow develops over a curved surface the coordinate system needs to be adapted.
We introduce a moving coordinate system that is based on the streamwise direction $s$, the wall-normal direction $n$ and the spanwise direction $z$.
The corresponding velocities are named as $u$, $v$ and $w$.
Hence, the Dirichlet condition with the velocity components $(1,0,0)$ is applied in the new coordinate system.
In \autoref{sec:flatTBL}, two different \acrshort{bc} configurations, the Dirichlet \acrshort{bc} and the \benennung{normal outflow} condition, on the top wall are compared in terms of their effect on the \acrshort{tbl} development.
These validations show that, ultimately, the differences on a flat \acrshort{tbl} are negligible, meaning that the Dirichlet \acrshort{bc} does not prevent the growth of the \acrshort{tbl}.
Therefore, we transferred this finding to the \acrshort{tbl} over a curved wall, which also simplifies the scenario setup.
The Dirichlet condition can be applied in the \texttt{f90} file, where the normal and tangential velocity components can be calculated and set as the user velocity. 
The normal outflow condition has been implemented in Neko, but currently only works for normal directions axis-aligned to a fixed $xyz$-coordinate system. 
The Blasius boundary layer was used as the initial condition similar to the flat \acrshort{tbl}.
In the curved segment the Blasius profile is rotated so that it builds up in the wall-normal direction. \\

\subsubsection{Mesh generation}
Transferring the presented simulation setups of the \acrshort{tbl} over curved walls to \name{OpenFOAM} requires some adaptations which will be presented here. 
First, the mesh has to be regenerated. 
It is not possible to use a mesh created in \name{gmsh} and transfer it to \name{OpenFOAM}, since the code must adapt the domain and the mesh after each iteration of the optimisation.
Therefore, the domain has to be regenerated with \verb|blockMesh| in every iteration.
As a consequence, the computational domain has to be defined in the \verb|blockMeshDict|.
To ensure that the results from the \name{OpenFOAM} simulation can be transferred into \name{Neko}, the setup must be quite similar.
Therefore, the computational domain has also a curved section as well as straight inlet and outlet regions similar to the constitution of the \acrshort{dns} domain.
However, the straight inlet is shorter than the one in the \acrshort{dns} domain.
The \acrshort{ic} for the \name{OpenFOAM} simulation is extracted at a position $s_{extr} = 275$ in the straight section of the \acrshort{dns} domain.
Therefore, the boundary layer in the \acrshort{rans} simulation only needs a much shorter straight inlet region to develop similar to the boundary layer in the \acrshort{dns}.
We defined the remaining length of the straight inlet as the remaining part of $s_{in} - s_{extr}$ and then added a balance zone of $s_{bal} = 20$ which ends up in a straight inlet of $s_{inOF} = 70$.
This balance region is recommended since quantities of the extracted \acrshort{dns} inflow profile have to be rebalanced in the \acrshort{rans} model \citep{morita_applying_2022}.
In \autoref{fig:openfoamDomain} the general configuration of the \acrshort{rans} domain is depicted exemplary for the R100deg30 case.
Compared to the domain used for the DNS, the height of the domain is increased to $10\delta_{0}$ for R100deg30 and R100deg90, and up to $20\delta_{0}$ for the case R500deg18.
This modification simplifies the transfer of the results of the optimised \name{OpenFOAM} simulation to the DNS domain, as described in \autoref{subsec:data_extr}.
To enable the adaption of the design points, the upper wall cannot be defined as a fixed circular arc in the curved section.
Instead, it is defined by the design points connected with a spline.
The optimisation code is constructed in a way that it modifies the position of the design points in the wall-normal direction. 


Since the wall-normal direction does not correspond to a fixed axis, the design points $\theta_i$ must be transformed into $x$- and $y$- coordinates to define the spline correctly.
This will be discussed in detail in \autoref{subsec:opt_settings}.
The lower wall is defined first as a straight edge and then transitions into a circular arc.
The straight outlet is not part of the spline, since there no optimisation is required.
It is meshed as a block with straight vertices.
The mesh resolution increases near the wall to ensure the first point being below $y^+ = 1$ measured from the lower wall.

\subsubsection{Boundary and initial conditions}
The quantities that require predefined \acrshort{ic} depend on the selected \acrshort{rans} model \citep{wilcox_turbulence_2006}. 
Since the $k\text{-}\omega\text{-}$ SST model is used in this project, it is necessary to define the \acrshort{ic} for turbulent kinetic energy $k$, dissipation $\omega$ and velocity $U$. 
This is achieved by applying an initial field for all these quantities at the inflow which is extracted from the previous \acrshort{dns} of the \acrshort{tbl} over a curved wall.
Therefore, a slice of the fully developed DNS simulation is used.
We take this slice at the streamwise position in the straight inlet region where $Re_{\theta} = 1000$ is reached.
At this streamwise position the fields of $U$, $k$ and $\omega$ are extracted across the entire height of the domain. 
In the spanwise direction the fields are already averaged which corresponds to the two-dimensionality of the \name{OpenFOAM} simulation.
In order to do this we perform a post-processing of the \acrshort{dns} using the \name{OpenFOAM} mesh as interpolation points.
With the \name{Python} package \texttt{fluidfoam} it is possible to read the points from an \name{OpenFOAM} mesh into \name{Python}. 
This is used to extract the points of the \name{OpenFOAM} mesh at its inflow.
These points are used as interpolation points to perform the post-processing. 
As described earlier the domain used in \name{OpenFOAM} is higher than the one for the \acrshort{dns}.
The usage of this higher domain would lead to interpolation conflicts since there are no data for the upper interpolation points. 
To avoid these conflicts the interpolation points lying beyond the height of the \acrshort{dns} domain are cut.
They will be filled manually at the end of the script.
The values for $U$ can be extracted directly, whereas $k$ and $\omega$ need to be computed. 
For this upper part of the inflow the last interpolated value is copied and added in the remaining cells.

\section{Optimisation method}\label{sec:OptimisationMethod}

This section introduces the procedure for generating a \acrshort{zpg} in the \acrshort{rans} simulation. 
This procedure is performed using \name{OpenFOAM} and the Bayesian optimiser code developed by \citet{morita_applying_2022}. 
The code is able to optimise the shape of the domain to achieve a given Clauser parameter at the lower wall.

In the following subsection the general workflow of the optimisation algorithm is outlined.
Then, the positioning of the design points is explained and additional settings for the optimisation are presented.


\subsection{Optimisation algorithm} \label{subsec:opt_settings}


\begin{figure}[h!]
    \centering
    \includegraphics[width=\textwidth]{optimisation/BOGP_flowchart_horizontal.pdf}
    \caption{Schematic visualisation of the workflow of the optimisation algorithm developed by \citet{morita_applying_2022}}
    \label{fig:optiFlowchart}
\end{figure}


The optimisation algorithm is based on a Bayesian optimisation with \acrfull{gpr}.
In this approach the connection between the design points and the \benennung{objective function} is modelled as a Gaussian process, providing both a predicted value and an estimate of the associated uncertainty at any point in the parameter space.
This surrogate is trained on a small set of \acrshort{rans} simulations and is updated after every evaluation.
An acquisition function then determines the next set of parameters to evaluate, balancing exploitation of the current best-known optimum against exploration of regions where the surrogate is most uncertain.
This treats the \acrshort{cfd} solver as a black box, which removes the need for gradient or adjoint information and keeps the number of required simulations low \citep{morita_applying_2022}.
This approach is particularly advantageous for scale-resolving turbulent flow simulations, whose objective functions are inherently noisy and expensive to evaluate \citep{talnikar_parallel_2014}.


The algorithm was first introduced by \citet{morita_applying_2022} and tested for different cases by \citet{ganagdhar_bayesian_2025}.
The workflow of the algorithm is depicted in \autoref{fig:optiFlowchart} and can be split into 6 steps.
First, the next samples for the design points are proposed by the \acrshort{gpr}.
The first iterations are randomly taken samples. 
Then, the \acrshort{gpr} suggests the next combination based on all previous iterations.
They are transferred into $x_{\theta_i}$ and $y_{\theta_i}$ to include them into the \texttt{blockMeshDict}.
In the next step the \name{OpenFOAM} simulation starts which consists of three steps.
First the new mesh is generated, then the case is split to the processors and then the simulation is run.
Once the \name{OpenFOAM} simulation ends, multiple boundary layer quantities are calculated to determine the Clauser parameter. 
With this, the residual, which is defined by the normalised $L^2$-norm of $\beta$, is calculated as
\begin{equation}
    R = \frac{\lVert \beta_{\text{eval}} - \beta_{\text{target}} \rVert_2}{\sqrt{N_{\text{eval}}}}
    \label{eq:residual}
\end{equation}

with $\beta_{eval}$ representing the calculated value in the current iteration.
$\beta_{target}$ is the objective function. 
The $L^2$-norm is normalised by the number of cells that are included in the evaluation window $N_{eval}$.
That is necessary for comparisons between residuals of different cases and respectively different evaluation window sizes.
In the next step the setup of the \texttt{OFcase} is stored if the residual is below a user-defined threshold.
That is beneficial to later compare different configurations with comparable good residuals.
In the last step the design points are added to the \texttt{gpList.dat} and the convergence check is performed.
These steps are repeated until the residual is converged or the maximum number of iterations is reached.

The general settings for the optimisation are the same for all simulations performed.
However, the number and position of the design points varies depending on the geometry of the case.
In \autoref{fig:OF_designPOints} the positioning procedure of the design points is visualised.
In all cases, the optimisation was started with five design points uniformly distributed over the curved section.

They are visualised in \benennung{Positioning 2} in \autoref{fig:OF_designPOints}.
In the final configuration, we used eight design points in the curved area for this case.
Optimisation of this setup revealed a sharp \acrshort{fpg} spike at the start of the wall curvature, not yet being controlled by the optimisation.
Since we wanted to enforce a \acrshort{zpg} already at the start of the wall curvature, we needed to modify the optimisation settings.
First, the current best setup was copied and the positions of its design points stored. 
In the new optimisation setup, the focus is on the part near the start of the curvature.
In order to manipulate the pressure gradient in this region, it was necessary to position additional design points in the straight inlet segment. 
We decided to add two more design points to obtain more control in this region and simultaneously ensure the sensitivity of all design points.
The first design point is positioned directly at the transition from the straight to the curved section.
The second one is positioned at $\frac{2}{3}s_{in}$ behind the inflow.
These additional points extend the evaluation window of $\beta$ at the lower wall beyond the beginning of wall curvature, which is depicted in green in \autoref{fig:OF_designPOints}. 
Since the length of this inflow region is quite small relative to the total length of the evaluation window, adding these points without changing the optimisation settings would not significantly affect the progression of $\beta$.

Additionally, this increases the optimisation dimension by two, which significantly slows down the optimisation process.
Therefore, we add these two points but modified the configuration in a way that the increase in the computational effort is prevented.
Since the optimisation performed for the curved segment only already produced quite good results, we adopted the optimised design points from there in the new setup. 
We fixed the six downstream design points in the curved section.
Moreover, we assumed that the inflow modification would not significantly impact the pressure field near the end of the curvature.
Thus, we only have two free design points in the curved section and two in the straight section in front of it which fastens the optimisation.
In addition, we applied a weight to the transition area of the evaluation window to increase the impact of the new design points.
We tested multiple other setups and distributions of the design points to ensure an accurate result.
For the other two cases we decided to directly follow the best working principle to position the design points directly.


As mentioned previously, we started with five design points in all cases.
For the case R500deg18, this resulted in small residuals.
This can be explained by the lower curvature in this case which reduces the natural pressure gradient caused by the curvature.
Therefore, the necessary compensation is much smaller. 
Additionally, the longer arc length provides more space for pressure changes, resulting in smaller gradients over the domain \citep{patel_longitudinal_1997}.
However, the R500deg18 case also shows a \acrshort{fpg} spike in the $\beta$ distribution at the transition from the straight to the curved section.
Therefore, as with R100deg30, we added two design points in the straight inlet section. 
We fixed the last four out of five points in the curved section reducing the optimisation problem to three dimensions with only the upstream points free.
With this configuration, it was possible to achieve a fairly good optimisation of the $\beta$ distribution.


For case R100deg90 we had to add several points in between the five initial design points.
Because of the small radius combined with the long curved segment in this case the natural pressure gradient is larger than in the other two cases.
Therefore, the optimisation has to compensate a higher pressure gradient.
To reach a proper level of the Clauser parameter we added design points in between each of the initially set ones ending up with 10 design points in the curvature.
Similar to the other cases, we then added two design points in the transition region.
Again only the two new and their two neighbouring design points are optimised in this run.
The other eight design points are fixed at their converged positions.

\subsubsection{Optimisation parameters}

Besides the positioning of the design points other parameters have to be determined for the optimisation algorithm.
For simplicity, all user-defined parameters are defined in a single \texttt{params.py} file.
There e.g.~the specific dimensions for the geometry of the domain can be defined, such as the radius, the length of the straight inlet and outlet segments and the angle.
In addition, the position of the design points in streamwise direction can be defined.
Regarding the design points, the \benennung{design space} also has to be limited for all design points.
We adapt their design space iteratively starting with the same wide range for all design points.
During the optimisation process we observe the motion of each design point in its range.
If design points tend over multiple iterations to a limit of their design space, we interrupt the optimisation and adapt their range correspondingly.
To avoid a steady extension of the design space, the opposite limit is also changed to keep the size of the design space constant.
The optimisation then can be restarted, and the old optimisation results are still taken into account from the \acrshort{bo}.
However, these adjustments require caution as hasty modifications can distort the exploration of the \acrshort{bo}.
Therefore, these adjustments should only be made if there is a long-term trend.
Concerning the optimisation algorithm, the evaluation window at the lower wall has to be defined.
As visualised in \autoref{fig:OF_designPOints} the evaluation window does not cover the complete bottom wall of the domain.
Instead, the evaluation window is confined to a section on which the modification of the design points has the capacity to exert an effect on $\beta$ at the lower wall.
The most important parameter is the definition of the objective function for $\beta$.


\subsubsection{Data extraction} \label{subsec:data_extr}

Once the optimisation of the Clauser parameter in \name{OpenFOAM} finished, the next step is to transfer the relevant quantities into the \name{Neko} simulation.
As stated before, the domain used for the \acrshort{dns} is less high in wall-normal direction. 
Therefore, the shape modification from the \acrshort{rans} simulation is not transferred.
However, only the quantities influenced by the shape adaptation are transferred.
Since the pressure itself is not directly adapted the velocity components build the defining quantities.
The velocity components are extracted at the height where the \acrshort{dns} domain has its upper wall, such that they can be imposed as \acrshort{bc}.
The extraction of the data from the \name{OpenFOAM} simulation is done with \name{Python}.
First the simulation with the best optimisation result is detected and stored in a separate directory.
The \name{Python} script reads the coordinates from the \texttt{C/Cx/Cy} files and the velocities from the corresponding fields. 
At a user-defined height the velocity values then are interpolated from the surrounding cells. 
The interpolated velocity are stored in a \texttt{csv} file. 
The integration of these values in the \acrshort{dns} is described in the next section.

\subsubsection{Velocity integration}

To run the \acrshort{dns} with \acrshort{zpg} the velocities extracted from \name{OpenFOAM} need to be applied as boundary condition on the \name{Neko} domain. 
This is implemented in the \texttt{user.f90} file. 
There the boundary points are read from the mesh. 
Then the streamwise position $s$ for the current point is calculated.
With this position the method \texttt{interpolate_velocity(s)} is called.
In this method the velocity is linearly interpolated form the surrounding velocity values read from the \texttt{csv} file.
This is done for all streamwise positions that are included in the \texttt{csv} file. 
Hence, also a part of the straight inflow in front of the curvature, and a part of the tail are included.
In the parts of the domain that are not included, $(1,0,0)$ is applied as before. 
To avoid sharp changes of the \acrshort{bc} when changing from $(1,0,0)$ to the optimised velocities, a blending is included.
This blends the edge value of the optimised velocities into the $(1,0,0)$ region in 10 length units in streamwise direction.
